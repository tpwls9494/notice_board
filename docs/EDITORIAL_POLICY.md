# JION 편집 기준 — 발견과 검증

핵심 질문은 ‘유명한 AI인가’가 아니라 ‘독자가 무엇을 새롭게 이해하거나, 자기 일에 어떻게 써볼 수 있는가’다. 익숙한 도구 이름 자체로 선정/제외하지 않는다. 읽고 변화의 의미를 이해하는 것만으로 완결되는 소식도 허용한다.

2026-09-09 개정: [50곳 비교](AI_CONTENT_BENCHMARK_50_20260909.md)와 사용자 피드백을 반영했다. [실행 계획과 첫 초안](CONTENT_EXECUTION_PLAN_20260909.md)을 따른다. 이 문서의 개정은 운영 발행 검사 코드 변경이나 자동 발행 활성화를 뜻하지 않는다.

## 글의 역할

| 역할 | 독자가 얻을 것 | 필수 내용 |
|---|---|---|
| 짧은 소식 | 무엇이 달라졌는지 | 핵심 변화·대상·주요 조건·원출처 |
| 해설 | 뉴스에서 생긴 궁금증의 답 | 질문에 대한 설명·구체적 사례·근거·한계 |
| 활용법 | 내 상황에 적용할 방법 | 결과 예시·준비 조건·방법·막히는 부분·검증 범위 |
| 경험·후기 | 실제로 해본 사람의 관찰 | 본인의 상황·시도·결과·사람의 개입·배운 점 |

- 위 역할은 편집 기준이며 새 상단 탭이나 현재 DB의 content_kind 값이 아니다. 논문은 원자료의 종류이므로 논문 기반 해설도 가능하다.
- 소식과 해설에 ‘직접 해보기’를 의무적으로 붙이지 않는다. 일반적인 체크리스트로 독자에게 검증을 떠넘기지 않는다.
- 활용법에서 직접 실행하지 않은 절차는 공식 안내 기반임을 밝힌다. 성공 여부·속도·품질을 확인한 것처럼 쓰지 않는다.
- 대표 해설은 원문을 열지 않아도 제목의 질문에 답해야 한다. 단순 번역·분량 확대는 자체 기여가 아니다.

## 선정 카드에 반드시 남길 내용

1. 새롭게 알게 될 점 한 문장. 일반 소개·인기·새 버전 번호만으로는 통과하지 않는다.
2. 기존 방식과 달라지는 점 및 그 근거. 새로운 제품뿐 아니라 특정 기능·구체적 사용법·의미 있는 제약도 후보가 된다.
3. 글의 역할과 독자가 얻을 답. 활용법은 실제 행동과 예상 첫 결과를 추가한다. ‘생각해보세요/문서를 읽으세요’만으로 실습형 글을 채우지 않는다.
4. 주요 접근 조건: 기기, 설치/모델 다운로드, 계정, 무료 한도, 비용, 입력 전송·보관 범위. 뉴스에서도 판단을 바꾸는 제한은 숨기지 않으며, 외부 실행을 권할 때는 상세 조건을 확인한다.
5. 확인 수준: 공식 설명 / 외부 사례 / 기본 동작 확인 / 동일 입력 비교를 구분한다.

스타·조회수·추천은 관찰 시각과 출처를 붙인 보조 근거다. 1만 스타는 필수 하한이 아니며, 낮은 누적 수치가 새 발견을 자동 탈락시키지 않는다. 측정하지 않은 증가량·사용자 수·성능은 채우지 않는다.

## 소싱

- 뉴스·뉴스레터에서 흥미로운 변화와 사례를 발견하고, 커뮤니티에서 실제 질문을 찾은 뒤 공식 발표·문서·논문으로 확인한다. 중간 규모 저장소의 실제 기능 릴리스, 익숙한 도구의 새 옵션/워크플로도 조사한다.
- 고정된 초대형 저장소 목록을 도는 것만으로 발굴을 완료했다고 하지 않는다.
- 최신 소식은 최근 7일의 원문 공개/의미 있는 변화를 우선한다. 기존 기능의 유용한 발견·해설은 그보다 오래돼도 가능하지만 최초 공개일과 현재 확인일을 구분한다. 커밋·재소개·플랫폼 제출 시각을 최초 공개일로 바꾸지 않는다.
- 공개 저장소·높은 조회수만으로 선정하지 않는다. 준비 부담에 비해 결과가 흥미로운지, 독자의 사용 또는 이해와 연결되는지를 먼저 판단한다.
- 50곳을 모두 자동 요약해 공개하지 않는다. 같은 발표를 옮긴 여러 기사는 독립 증거 여러 개가 아니다. 원문·이미지·경험담의 재사용 조건을 확인하고, 사용자의 경험을 옮길 때 동의와 맥락을 보존한다.
- 같은 발견을 다른 제목·다른 URL로 반복하지 않는지 검토한다. 현재 코드의 URL 중복 검사가 의미 중복까지 해결하는 것은 아니다.

## 제목과 목록 소개

- 제목은 하나의 발견·문제·대조에 집중한다. 목표는 공백 포함 18~32자이며 영어 도구명 때문에 길어지면 부연을 소개문으로 옮긴다. 긴 제목 뒤에 콜론으로 설명을 계속 덧붙이지 않는다.
- 목록 소개는 핵심 한 문장, 목표 40~80자다. 독자가 무엇을 알거나 할 수 있는지 구체적으로 쓰고 프리뷰/유료 요금제/검토 논문 같은 판단에 중요한 조건은 남긴다.
- 제목의 궁금증은 본문이 실제로 답할 수 있어야 한다. 미측정 비용 절감·속도 향상, 검증되지 않은 성공담이나 ‘무조건/완벽/충격’ 표현을 만들지 않는다.
- 원문 제목은 상세 출처 영역에 보존하고 목록에서 한국어 제목·긴 설명·영문 제목을 세 겹으로 반복하지 않는다.
- 짧은 소개는 본문이나 실습 검증을 대신하지 않는다. 본문의 구성과 소제목은 글의 질문에 맞추고, 필요한 조건·근거를 남긴다. 발표 소개와 재현한 실습을 구분한다.
- 원문은 본문을 읽은 뒤 더 확인할 자료다. 같은 원문으로 가는 버튼을 반복하지 않는다. 근거 링크와 원저자 표시는 숨기지 않는다.
- 비교표·결과 화면은 이해를 도울 때만 사용한다. 본문과 무관한 이미지나 임의로 생성한 ‘실험 결과 화면’을 넣지 않는다.

## 직접 실행의 기준

- 설치 성공은 기본 동작 확인이지 차별점 검증이 아니다.
- 비교 주장이 있으면 동일 입력·공통 설정·평가 기준을 고정한다. 모드 차이는 기록한다.
- 품질·시간을 함께 보고, 첫 실행/모델 초기화/준비 후 실행/다운로드를 구분한다.
- 유리한 결과만 고르지 않는다. 표준/대조 방식도 실패했다면 함께 기록한다.
- 쉬운 활용법은 ‘노트북 또는 브라우저에서 15분 안에 첫 결과’를 권장 목표로 삼되, 모든 소재의 탈락 기준으로 쓰지는 않는다. 시간이 더 필요한 소재는 이유·준비 부담·기대 결과를 먼저 설명한다. 시간 주장을 할 때는 설치·다운로드·가입의 포함 여부와 측정 환경을 밝힌다. 준비된 개발 환경의 실행 시간만으로 통과 표시하지 않는다.
- 실제로 재현하지 못한 논문은 연구 설명으로 분류하고, 실습형 글 자리에는 억지로 넣지 않는다. 별도 실행 승인이 필요하면 보류하고 사용자에게 조건을 알린다.
- 외부 데모에 계정·비밀키·고객 데이터·업무 명세를 임의로 보내지 않는다. 데이터 이용 범위가 넓은 새 서비스의 제출은 먼저 검토한다.

## 모델 협업

사용자가 Fable에 검토 요청을 전달하고 결과를 가져오는 흐름을 따른다. 직접 Claude 호출을 요청받은 것으로 확대 해석하지 않는다. 검토 의견 전체를 읽되 최종 사실은 원문·실험과 대조한다. 모델 간 동의는 독립 검증을 대신하지 않는다.

공개 전에는 제목의 질문에 대한 답, 원문 수치의 비교 대상·지표·평가 주체·조건, 실제 확인 범위가 갖춰졌는지 검토한다. 활용법에는 실행 조건과 첫 행동을 추가로 검토한다. 기준 미달 글을 개수에 맞춰 발행하지 않는다.

## 대화와 발행

- 짧은 질문·관찰은 기존 댓글로, 긴 사용 기록은 기존 후기 글로 받는다. 댓글에 카테고리 선택을 다시 요구하거나 같은 내용을 두 번 작성하게 하지 않는다.
- 글에서 자연스럽게 남는 질문을 하나 제안할 수 있지만 모든 글에 억지 질문을 붙이지 않는다. 가짜 회원·댓글·사용 효과로 참여를 연출하지 않는다.
- 로컬 초안, 서버 검토함 등록, 공개 발행, 자동화 활성화는 별개의 상태로 보고한다. 한 단계 승인을 다른 단계의 승인으로 해석하지 않는다.
- 유료 API 호출은 목적·범위·예산을 먼저 알린다. 새로운 저장·구독·알림 기능은 사전 고지 후 진행한다.

이 문서는 편집 정책이다. 모든 조건을 자동 판별하는 코드나 정기 발행 기능이 이미 배포됐다는 뜻은 아니다.
