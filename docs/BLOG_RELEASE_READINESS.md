# 블로그 운영 반영 준비 — 2026-09-06

현재 상태는 **구현 및 격리 환경 검증 완료, 운영 배포 전**이다. 운영 DB 백업이나 운영 코드 교체는 아직 실행하지 않았다.

## 이번에 보완한 내용

- 이메일 로그인 후 사용자 확인과 원래 화면 복귀. 만료된 인증은 제거하고 관리 화면의 접근을 종료한다.
- Google / GitHub 로그인 버튼과 블로그 콜백 화면. 기존 본사이트 OAuth 시작·콜백 주소를 사용하고, 서명된 state의 `site=blog`로 블로그에 복귀한다. 기존 본사이트 로그인 경로는 유지한다.
- 로그인·관리·작성·초안 화면은 검색 제외 처리한다. 공개되지 않은 글의 서버 HTML은 제목이나 본문을 노출하지 않고 404를 반환한다.
- Nginx가 공개 글의 HTML을 백엔드에 요청해 제목·설명·대표 이미지·canonical·구조화 데이터를 넣는다. 이 과정에서는 조회수를 올리지 않는다. SPA 내부 이동 시에도 메타 정보를 갱신한다.
- 블로그 전용 1200×630 PNG 공유 이미지와 robots.txt. sitemap에는 발행된 글만 포함한다.
- 블로그 요청 한도를 11MB로 조정해 10MB 본문 이미지와 multipart 부가 데이터를 처리한다. 프로필 이미지는 API에서 별도로 5MB를 제한한다.
- `npm audit fix`로 허용된 버전 범위 안에서 의존성을 수정했다. 로컬 및 Linux npm 검사 결과는 0건이다.

메타 정보 구성은 [Open Graph](https://ogp.me/), 검색 제외·JavaScript 렌더링은 [Google Search Central](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics)의 동작을 기준으로 검토했다.

## 배포 구성

`Dockerfile.nginx`가 빌드한 블로그 index.html을 시작 스크립트 `nginx/40-blog-template.sh`가 공유 볼륨에 복사한다. 백엔드는 `blog_template` 볼륨을 읽기 전용으로 마운트한다. JS·CSS·이미지 같은 정적 파일은 계속 Nginx에서 제공한다.

- `BLOG_PUBLIC_ORIGIN`: 기본 `https://blog.jionc.com`. canonical, sitemap, 블로그 OAuth 복귀 주소에 사용한다.
- `BLOG_HTML_TEMPLATE`: 기본 `/app/blog-template/index.html`. 운영 Compose의 공유 볼륨 경로다.
- `VITE_AUTH_ORIGIN`: 필요할 때만 변경한다. 기본 `https://jionc.com`의 기존 OAuth 공급자 콜백 설정을 사용한다.
- 마이그레이션 head: `202609050004`. 블로그의 반응·프로필 테이블뿐 아니라 앞선 본사이트 마이그레이션도 연결되어 있다.
  - 후속 본사이트·블로그 댓글 변경 이후 공유 DB의 최신 head는 `202609060002`다. 이 문서의 `202609050004`는 초기 블로그 검증 당시 기록이며 [댓글 통일 검증](COMMENT_UNIFICATION.md)의 블로그 절을 함께 확인한다.
- `.dockerignore`에 로컬 테스트 DB, 업로드 데이터, 환경 파일, node_modules를 제외했다. 체험 계정·예시 데이터·검증용 인증서는 운영 빌드에 포함하지 않는다.

## 실제 배포 전에 필요한 정보

1. SSH 접속 주소 또는 등록된 별칭, 프로젝트가 설치된 절대 경로.
2. 작성자 계정의 실제 로그인 방식과 로그인 후 권한 확인.
3. 함께 작업 중인 jionc.com 변경의 배포 범위. 현재 `Dockerfile.nginx`는 두 프런트엔드를 함께 빌드하고, 백엔드도 공유한다. 현재 작업 폴더 전체를 그대로 배포하면 본사이트 개편도 포함된다.

## 운영 반영 순서

2026-09-06 통합 보완 이후의 실행 기준은 [통합 배포 검증·운영 절차](INTEGRATED_RELEASE_READINESS.md)다. 아래는 블로그 단독 준비 당시 기록이며, 현재는 `bash deploy.sh --confirm-downtime`을 사용한다. 빌드 후 두 서비스를 중단해 백업하며, 별도 백업 선실행은 필요 없다. 운영 배포는 여전히 실행하지 않았다.

1. 서버의 현재 커밋·실행 이미지·DB revision·업로드 볼륨을 읽기 전용으로 확인한다. 위 배포 범위를 먼저 맞춘다.
2. 변경 소스를 누락 없이 준비한다. 새 Python/React 파일, `40-blog-template.sh`, 마이그레이션 003·004가 포함되어야 한다.
3. 배포 동안 글·프로필·이미지 변경이 진행되지 않도록 운영 시간을 잡는다.
4. `bash scripts/backup-release.sh`로 DB custom dump와 `/app/uploads` 아카이브, 이미지 ID와 체크섬을 저장한다. 덤프·아카이브 검증에 실패하면 중단한다. `deploy.sh`도 이 백업을 먼저 실행한다.
5. `bash deploy.sh`는 이미지 빌드 후 마이그레이션을 별도 컨테이너에서 확인하고 애플리케이션을 갱신한다. DB를 포함한 전체 `down`은 하지 않으며 이전 이미지를 자동 정리하지 않는다.
6. 운영 도메인에서 로그인·CRUD·프로필·이미지 업로드·공유 HTML·사이트맵을 다시 확인한다. 실제 운영 계정의 로그인은 이 단계에서도 본인 확인이 필요하다.

되돌릴 때는 이전 이미지 ID와 DB·업로드 백업을 함께 사용한다. DB 복원은 운영 DB를 바로 덮어쓰기보다 별도 DB에 먼저 복원해 검증한 뒤 전환한다. 복원·롤백은 이번 작업에서 운영 서버에 실행하지 않았다.
